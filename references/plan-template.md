# 需求文档与实施计划模板

正文面向需求方，沿用下列六节的标题和顺序。只要求需求文档时使用正文。节内细项按任务取舍，影响范围的未知信息标为「待确认」。保存位置按 `SKILL.md` Phase 2 选择。

完整规划默认保存到项目根目录的 `plans/YYYY-MM-DD-<任务名>.md`。同一任务持续更新同一文件。保存后返回绝对路径链接和版本。工程附录按需填写，无相关内容时简述原因，已有内容通过编号引用。

## 各节写作要点

| 节 | 常见错误 | 正确做法 |
|----|----------|----------|
| 项目目标 | 只写开发动作 | 写交付后使用者能完成什么 |
| 用户与终端 | 默认所有人、所有平台 | 写明确的使用角色、入口和支持范围；未知项标为待确认 |
| 呈现方式 | 给纯接口或后台任务补造页面 | 写调用方、入口、输入和输出，按需补充界面信息 |
| 本期范围 | 把候选功能混进交付 | 列出本期需求与容易混淆的范围外事项 |
| 现状调研 | 复述需求文档 | 写从代码里读到的事实，含文件路径 |
| 交付与验收 | 只列代码文件或写「功能正常」 | 写清可使用的成果、从哪里验证和预期结果 |
| 任务拆解 | 任务粒度过大（"完成后端"） | 每个任务有明确的产出物、完成边界和验收方式 |
| 实施顺序 | 与依赖列矛盾 | 写完后按顺序走一遍依赖图，确认无环、无前置缺失 |
| 风险 | 只写技术风险 | 已知未知（待用户决策的）也算，这类放确认门里问 |
| 可行性评审 | 三项全写"无问题"，无证据 | 每项给证据或证据缺口；标出前置条件、通过标准和受影响的任务 |
| 方案建议 | 口号式建议（"注意代码质量"）；与评审结论脱节 | 每条有可执行动作和可追溯来源；纳入本期时同步检查任务、依赖、顺序和验收项 |
| 保存与恢复 | 根据当前子目录建新计划，或仅凭修改时间选文件 | 明确项目归属，复用同任务文件，交接时提供路径和版本 |
