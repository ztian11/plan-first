# 实施规划文档模板

完整规划使用本模板。空项写明原因，保存位置按 `SKILL.md` Phase 2 选择。

---

```markdown
# 实施规划：<任务名>

> 当前状态：<待评审 / 待确认 / 已确认 / 执行中 / 受阻 / 已完成>
> 创建：<日期>　当前版本：v1
> 确认记录：<日期、已确认版本、范围及关键决定，或待确认>

## 1. 背景与目标

- **背景**：一句话说清为什么做这件事
- **目标**：完成后达到什么状态（1–3 条，可判断达成与否）
- **非目标**：明确不做什么，防止范围蔓延

## 2. 现状调研结论

> Phase 1 的产出。凭空假设工程约定是规划事故的第一来源。

- 技术栈 / 版本：
- 相关模块与入口：
- 已有约定（目录 / 命名 / 风格 / 测试）：
- 硬约束（体积 / 兼容 / 依赖许可）：

## 3. 验收标准

> 可验证的完成定义。每条必须能独立判断真伪，避免"基本完成"。

- [ ] AC1：<可验证的表述>
- [ ] AC2：
- [ ] AC3：

## 4. 任务拆解

| ID | 任务 | 优先级 | 依赖 | 预期产出 | 验收方式 | 状态 |
|----|------|--------|------|----------|----------|------|
| T1 |  | P0 | — |  |  | ⬜ |
| T2 |  | P0 | T1 |  |  | ⬜ |
| T3 |  | P1 | T1 |  |  | ⬜ |
| T4 |  | P2 | — |  |  | ⬜ |

优先级：P0 核心路径（缺失即失败）/ P1 应有（不阻塞核心）/ P2 可延后。
粒度：单个任务可在一次专注会话内完成。

**任务记录**：任务完成时记录 ID、验收结果和证据位置。受阻时记录原因、解锁条件。中断的有副作用操作记录已知执行结果及恢复方式。

## 5. 实施顺序

> 在已确认且前置条件已通过的任务中，依赖优先，同层级按 P0 → P1 → P2。

T1 → T2 →（T3 ∥ T4）
里程碑 M1 = T1 + T2 完成（最早可演示 / 可验证的节点）

## 6. 风险与待确认项

| 风险 / 疑问 | 受影响任务 | 应对 / 需要的决策 |
|-------------|------------|-------------------|
|  |  |  |

涉及外部副作用时，记录环境、所需授权、如何核对执行结果以及重试或回滚条件。

## 7. 可行性评审结论

> Phase 3 第一步的产出。每项记录结论及证据（文件路径 / 实测结果 / 引用）或证据缺口。

- 评审结果：✅ 通过 / ⚠️ 有条件通过 / ❌ 打回修订 / ⛔ 受阻
- **假设冲突**：<设计假设与代码/数据/依赖实际情况的比对结论；证据：>
- **未知当已知**：<被当作"已知"但未验证的条目清单；处置：验证 / 降级为假设 / 前置验证任务：>
- **返工缺口**：<最可能导致推倒重来的缺口；前置动作（已入任务表，任务 ID：）：>

| 前置任务或阻塞项 | 通过标准或解锁条件 | 受影响任务 ID | 当前结果及证据 |
|------------------|--------------------|---------------|----------------|
|  |  |  |  |

前置验证作为独立 P0 任务入表，并列入受影响任务的依赖。核验后记录结果，更新评审状态。

## 8. 方案建议

> Phase 3 第二步的产出。每条建议必须具体、可操作，并能追溯到第 7 节的评审发现或第 2 节的现状调研；与评审结论矛盾的建议不许出现。

### 8.1 实施建议（如何落地执行）

> 说"怎么做才能顺"，不重复任务表的"做什么"。

- **实施步骤**：<环境准备 / 执行顺序调整 / 验证节点>
- **注意事项**：<易错点 / 需提前准备的资源>

### 8.2 优化建议（方案中可改进之处）

| 建议 | 优化方向 | 处置 |
|------|----------|------|
|  |  | 拟纳入本期（任务 ID）/ 本期已确认（任务 ID）/ 下迭代 / 仅记录 |

> 只将本期建议和必要前置动作纳入任务表。涉及范围扩大的本期建议，等待用户确认后执行。

### 8.3 修改建议（现有实现 / 方案设计的问题 → 明确改法）
```

## 各节写作要点

| 节 | 常见错误 | 正确做法 |
|----|----------|----------|
| 背景与目标 | 目标写成动作（"实现登录功能"） | 目标写成状态（"用户可凭账号完成登录并保持会话"） |
| 非目标 | 省略不写 | 至少写一条；最容易被顺带做进去的事放这里 |
| 现状调研 | 复述需求文档 | 写从代码里读到的事实，含文件路径 |
| 验收标准 | "功能正常" | 给可执行命令 / 可点击路径 / 可观测结果 |
| 任务拆解 | 任务粒度过大（"完成后端"） | 每个任务有明确的产出物、完成边界和验收方式 |
| 实施顺序 | 与依赖列矛盾 | 写完后按顺序走一遍依赖图，确认无环、无前置缺失 |
| 风险 | 只写技术风险 | 已知未知（待用户决策的）也算，这类放确认门里问 |
| 可行性评审 | 三项全写"无问题"，无证据 | 每项给证据或证据缺口；标出前置条件、通过标准和受影响的任务 |
| 方案建议 | 口号式建议（"注意代码质量"）；与评审结论脱节 | 每条有可执行动作和可追溯来源；纳入本期时同步检查任务、依赖、顺序和验收项 |
