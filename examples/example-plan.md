# 实施规划：为博客站点新增用户登录功能（示例）

> 以下为虚构的登录改造示例，包含演示用的验收记录。

> 当前状态：🚧 执行中
> 创建：2026-10-12　当前版本：v4
> 确认记录：2026-10-12，用户确认 v4 的开发环境改造范围 T1–T7。上线另行决策。

## 1. 背景与目标

- **背景**：个人博客当前无用户体系，评论功能要求登录后使用
- **目标**：
  1. 用户可凭邮箱和密码注册、登录、登出。在服务持续运行时，会话自登录起有效 7 天
  2. 评论提交时自动关联当前用户
- **非目标**：生产部署、重启后的会话恢复、OAuth、密码找回、后台用户管理

## 2. 现状调研结论

- 技术栈 / 版本：Express 4.19 + EJS + SQLite（better-sqlite3），无 ORM
- 相关模块与入口：`routes/posts.js`（含评论提交 POST `/posts/:id/comments`，登录态为内联判断）、`db/index.js`（建表入口）
- 已有约定：路由按资源分文件；`db/migrations/` 下手工 SQL 迁移，按序号命名；无测试框架（本次不引入）
- 硬约束：单机部署，SQLite 不换；不新增付费依赖

## 3. 验收标准

- [x] AC1：注册后可用邮箱和密码登录，刷新时会话有效。用可控时钟验证登录后第 6 天仍有效，达到 7 天后要求重新登录。主动登出后评论入口恢复未登录态
- [ ] AC2：未登录访问评论提交 POST 跳转登录页，登录后回到原页面
- [ ] AC3：数据库中评论记录关联用户 ID，旧评论（匿名）正常显示"匿名"
- [x] AC4：密码存储为 bcrypt 哈希，数据库中无明文密码

## 8. 方案建议

### 8.1 实施建议（如何落地执行）

- **实施步骤**：
  1. 迁移前备份 `data/blog.db`，T7 在隔离副本用等价 SQL 预演 T4 的表结构变更。
  2. T7 通过后记录查询结果并更新评审状态，再执行 T4。T7 失败时暂停 T4，根据结果修订或恢复隔离副本。
  3. T4 完成后复核 AC1–AC4，作为里程碑 M1 的出口条件。
- **注意事项**：
  - `db/migrations/` 按序号命名，当前规划使用 003。后续变更使用新编号，保留已执行迁移的记录。
  - 涉及会话的路由改动，登录 / 未登录两种状态各验证一次（现状调研：`routes/posts.js` 内联判断登录态，容易只测一种状态）
  - 改动 express-session cookie 配置后清一次浏览器 cookie 再测，避免旧 cookie 干扰判断
