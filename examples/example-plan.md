# 实施规划：为博客站点新增用户登录功能（示例）

> 这是一个已填充完整的示例规划，演示模板的实际用法。你的规划应基于真实调研产出，不要照抄本示例的结构性内容。

> 状态：✅ 已确认
> 创建：2026-10-12　确认：2026-10-12（用户）　规划版本：v4（v3 基础上增补方案建议，见变更记录）

## 1. 背景与目标

- **背景**：个人博客当前无用户体系，评论功能要求登录后使用
- **目标**：
  1. 用户可凭邮箱 + 密码注册、登录、登出，会话保持 7 天
  2. 评论提交时自动关联当前用户
- **非目标**：不做 OAuth 第三方登录、不做密码找回（下个迭代）、不做管理后台用户管理

## 2. 现状调研结论

- 技术栈 / 版本：Express 4.19 + EJS + SQLite（better-sqlite3），无 ORM
- 相关模块与入口：`routes/posts.js`（含评论提交 POST `/posts/:id/comments`，登录态为内联判断）、`db/index.js`（建表入口）
- 已有约定：路由按资源分文件；`db/migrations/` 下手工 SQL 迁移，按序号命名；无测试框架（本次不引入）
- 硬约束：单机部署，SQLite 不换；不新增付费依赖

## 3. 验收标准

- [ ] AC1：注册后用邮箱密码登录，刷新页面会话保持，登出后评论入口回到未登录态
- [ ] AC2：未登录访问评论提交 POST 跳转登录页，登录后回到原页面
- [ ] AC3：数据库中评论记录关联用户 ID，旧评论（匿名）正常显示"匿名"
- [ ] AC4：密码存储为 bcrypt 哈希，数据库中无明文密码

## 7. 可行性评审结论

- 评审结果：⚠️ 有条件通过
- **假设冲突**：规划初稿假设评论表可直接挂用户 ID——实际 `comments` 表只有 `guest_name` 列，无 `user_id`（证据：`db/migrations/001_init.sql` 第 12–18 行）。已决策：`003_comments_user_id.sql` 迁移并入 T4，不影响任务边界。
- **未知当已知**：bcrypt 与 better-sqlite3 在本机 Node 18 下的原生编译未验证过，初稿默认"能装"。处置：实测 `npm install` 通过（2026-10-12），从假设转为已验证。
- **返工缺口**：会话存储——若开发期直接用内存 store、上线前才换 connect-sqlite3，store 配置要重写一遍。前置动作：T3 中把 store 初始化抽为独立函数 `config/session-store.js`，切换时只改一处（已并入 T3 产出）。

## 8. 方案建议

### 8.1 实施建议（如何落地执行）

- **实施步骤**：
  1. 动任何迁移前先备份 `data/blog.db`——T4 加列涉及存量数据
  2. T1 迁移写完后立即在开发库实测建表 + 插入 + 查询（bcrypt 原生编译已在评审中验证，无环境阻塞）
  3. T2 / T3 并行推进，各自用 curl 验证通过后再合并
  4. T4 完成后跑一遍 AC1–AC4 全量验收，作为里程碑 M1 的出口条件
- **注意事项**：
  - `db/migrations/` 按序号命名，新迁移必须接续编号（下一号为 004），禁止复用已执行过的编号
  - 涉及会话的路由改动，登录 / 未登录两种状态各验证一次（现状调研：`routes/posts.js` 内联判断登录态，容易只测一种状态）
  - 改动 express-session cookie 配置后清一次浏览器 cookie 再测，避免旧 cookie 干扰判断

### 8.2 优化建议（方案中可改进之处）

| 建议 | 优化方向 | 处置 |
|------|----------|------|
| users 表补 created_at / updated_at 基础字段 | 排查与审计的基础数据；趁 `002_users.sql` 尚未执行到生产，加列成本几乎为零 | 本期采纳（T8） |
| 登录态判断抽为 authMiddleware | `routes/posts.js` 内联判断登录态，新增受保护路由时容易漏判；抽中间件后 T4 只需挂载 | 下迭代（涉及存量路由改造，超出本期非目标边界） |
| 迁移执行记录表 | 手工迁移靠编号约定 + 人工记忆"执行到几号"，一张 `_migrations` 表可机器判断 | 仅记录（单机单人开发，收益暂不抵成本） |

### 8.3 修改建议（现有实现 / 方案设计的问题 → 明确改法）

| 问题 | 修改方案 | 理由 |
|------|----------|------|
| `comments` 表无 `user_id` 列，与 AC3 直接冲突（评审"假设冲突"项） | T4 前执行 `003_comments_user_id.sql`：新增**可空** `user_id` 列 + 索引；存量数据保持 NULL，渲染时显示"匿名" | 直接按非空外键建列会因存量匿名数据而失败；可空列对既有数据零破坏，改动最小且可回滚 |
| 规划 v2 将会话 store 配置直接写在 app.js 入口（评审"返工缺口"项） | 抽 `config/session-store.js` 暴露 `getStore()`，开发/生产按环境变量切换；app.js 只调用不实现 | 上线前换 connect-sqlite3 时只改一个文件；入口保持薄，与项目"路由按资源分文件"的既有分层约定一致 |
